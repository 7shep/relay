## Problem Statement

Relay currently has a local-first dashboard with a Qwen sidebar for operational school-life work: importing syllabi, extracting deadlines, drafting focus tasks, and organizing the day. The next product surface is intentionally separate: a deeper agent workspace for learning course material and improving assignment outcomes.

The workspace will use Luna 5.6 through the user's Codex usage and will start with two specialists:

- Tutor agent: teaches concepts and adapts from demonstrated performance across courses.
- Assignment agent: understands prompts and rubrics, plans the work, reviews drafts, and prioritizes revisions.

This workspace is not another task manager. It may produce optional actions that the user can send to the Qwen sidebar, but it must not silently create focus tasks.

## What Makes This Cool

The workspace becomes a learning loop rather than a collection of chatbots. The Assignment agent can detect a rubric weakness, automatically invoke the Tutor to repair the underlying concept, observe whether the user improves, and send the updated evidence back into assignment review.

The long-term differentiator is a cross-course learner model based on behavior: misconceptions, repeated mistakes, successful explanations, pacing, and demonstrated mastery. It should show what it believes, why it believes it, and how confident it is.

## Constraints

- Keep the existing Qwen/Ollama sidebar focused on tasks, planning, and organization.
- Use Luna 5.6 for the deep agent workspace; the exact Codex usage integration contract is still an open question.
- Start with Tutor and Assignment agents only. Defer a third agent until these two workflows prove useful.
- Automatic orchestration is in scope for agent-to-agent handoffs, not for task creation or submission of academic work.
- Course materials, drafts, rubrics, and learner history are sensitive personal data. Storage, retention, export, and deletion must be explicit.
- Preserve the current React/Vite browser app and its local-first direction where practical.
- The current app persists simple data in `localStorage`; agent research requires structured run history, learner signals, and artifacts that can be queried and migrated.

## Premises

1. The Qwen sidebar is the operational assistant; the Luna workspace is the deep academic environment.
2. The workspace has two specialists for now, with automatic orchestration between them.
3. The Assignment agent follows one lifecycle: understand the prompt and rubric, plan the work, review drafts, simulate likely grading, and prioritize revisions.
4. The Tutor builds a cross-course learner model from observed behavior rather than relying only on stated preferences.
5. Agent actions are visible and explainable: the workspace shows which agent acted, why it acted, what context it used, and what evidence supports the result.
6. The system helps the student understand and improve their work. It does not silently produce a final submission or claim that an estimated grade is authoritative.

## Approaches Considered

### Approach A: Workspace state machine

The smallest useful version would add explicit course and assignment sessions, two agent modes, structured outputs, and a simple orchestrator. It reuses the current component and persistence patterns and would prove the learning loop fastest. Rejected for now because the user wants the workspace to double as a durable agent-research environment.

### Approach B: Durable agent runtime

The selected approach. Build around structured agent runs, events, shared context, handoffs, learner-model updates, retries, and evaluation results. This creates a researchable system where the user can inspect not only the answer but also the chain of decisions that produced it.

### Approach C: Academic knowledge graph

Represent courses, concepts, rubric criteria, assignments, mistakes, evidence, sessions, and mastery as connected nodes. This remains a possible future direction, but it is deferred until the runtime produces reliable artifacts worth connecting.

## Recommended Approach

Build a durable, local-first agent runtime behind a dedicated academic workspace.

### Workspace shape

- Workspace rail: courses, assignments, study sessions, recent agent runs, and learner-model summary.
- Main canvas: the current course, assignment, rubric, study material, draft, or tutoring session.
- Agent activity pane: current agent, handoffs, status, source context, structured output, and user controls.
- Explicit output actions: save to workspace, apply to the assignment plan, start a Tutor session, export notes, or send a selected action to the Qwen sidebar.

### Core runtime records

- `Course`: course identity and course-specific source materials.
- `Assignment`: prompt, due date, type, source, and current lifecycle stage.
- `RubricCriterion`: criterion text, weight, evidence expectations, and current assessment.
- `Artifact`: syllabus excerpt, rubric, notes, draft, feedback, quiz attempt, or session summary.
- `AgentRun`: agent name, input artifact IDs, model/provider, start/end state, output artifacts, and errors.
- `Handoff`: source agent, target agent, reason, input/output artifacts, status, and whether user approval was required.
- `LearnerSignal`: observed answer, mistake, hint usage, successful explanation, confidence, and supporting artifact.
- `LearnerProfile`: cross-course strengths, weak concepts, recurring patterns, confidence, evidence links, and correction history.

### Orchestration loop

1. The user opens an assignment, course, or study session.
2. The orchestrator classifies the current need from workspace state and recent artifacts.
3. It invokes the appropriate specialist with only the context needed for that run.
4. The specialist returns structured output plus evidence links and uncertainty markers.
5. The runtime validates and stores the output as an artifact and appends an agent-run event.
6. If the output exposes a need for the other specialist, the orchestrator creates a visible handoff with a reason and runs it.
7. The user sees the combined result, can inspect the trace, and chooses which artifacts or actions to keep.
8. Observed learning signals update the learner model. Updates remain reversible and evidence-linked.

### Assignment agent lifecycle

- Intake: parse prompt, rubric, format, deadline, constraints, and missing information.
- Rubric map: translate every criterion into observable evidence and common failure modes.
- Plan: create phases, milestones, definitions of done, and a time-aware sequence.
- Work support: answer assignment-specific questions, find gaps, and request Tutor help when a concept is missing.
- Draft review: evaluate the draft criterion by criterion, quoting or pointing to evidence rather than giving generic praise.
- Grade simulation: estimate a range or rubric state with confidence and explain what could move the result. Never present it as the instructor's actual grade.
- Revision queue: identify the highest-impact changes and verify them in a later run.

### Tutor agent behavior

- Teach from course materials and the user's demonstrated level where available.
- Prefer questions, hints, retrieval practice, examples, and small checks over immediately giving answers.
- Adjust difficulty, pacing, explanation style, and amount of scaffolding based on observed performance.
- Record misconceptions and successful repairs as learner signals.
- Revisit recurring weaknesses across courses without treating a weak attempt as a permanent ability label.
- Produce a session summary with concepts covered, evidence of understanding, remaining uncertainty, and a recommended next check.

### Trust and academic-integrity boundaries

- Every material claim should identify its source or be labeled as an inference.
- Rubric feedback should map to the exact supplied rubric, not a generic grading standard.
- Grade simulation must be framed as an estimate with evidence and uncertainty.
- The system should default to coaching, critique, and practice. Any drafting assistance must be clearly labeled and user-invoked.
- Automatic orchestration can start agent runs, but it cannot submit work, overwrite a draft, or create sidebar tasks without explicit user action.
- The learner model must support inspect, correct, export, and delete operations.
- Agent runs need cancellation, retry, and failure states so a Luna outage does not look like a successful learning result.

### Provider boundary

Keep model access behind an agent-provider adapter. The workspace should not assume that a browser can safely hold Codex credentials or that Luna 5.6 has the same API shape as Ollama. The adapter should expose model identity, streaming, structured output, cancellation, usage/error metadata, and a provider health state. The exact bridge for Luna through Codex usage must be resolved before implementation.

## Open Questions

- What is the supported programmatic integration for Luna 5.6 through Codex usage: local bridge, authenticated service, or another runtime?
- Should agent data remain browser-local, move to IndexedDB, or use a local companion service for the event log?
- Which materials must be ingested first: syllabus, rubric, PDF readings, slides, notes, images, or code repositories?
- Should source-grounded research be part of the Assignment agent or remain deferred until a third specialist is justified?
- What exact evidence is sufficient to update mastery or a recurring-mistake record?
- How should the orchestrator behave when the Assignment and Tutor agents disagree?
- Which handoffs may run automatically, and which require a confirmation because they consume model usage or expose sensitive data?
- What academic-integrity rules apply to each course or assignment, and how should the user record them?
- How should the workspace surface a model failure, unsupported file, missing rubric, or stale learner-model assumption?

## Success Criteria

- A user can create a course workspace from existing assignment and rubric material without retyping the same context for every agent run.
- The Assignment agent produces a criterion-by-criterion map, a plan, draft feedback, and a revision queue in one resumable workspace.
- The Tutor can be invoked automatically from a detected assignment weakness and returns a study session tied to that weakness.
- The learner model shows evidence-backed cross-course patterns and allows the user to correct or remove them.
- Every automatic handoff is visible in the activity trace with a reason, inputs, outputs, and failure state.
- No agent run silently creates tasks in the Qwen sidebar or changes a draft.
- A user can resume a workspace after closing the browser without losing artifacts, run history, or learner-model updates.
- The system can distinguish sourced facts, model inferences, estimates, and user-provided information.
- The provider adapter can report Luna availability and usage errors without misrepresenting a failed run as completed.

## Distribution Plan

Continue distributing the core app as the existing local browser app through `npm run dev` during research. The Luna provider boundary should use a local companion bridge or other secure server-side path rather than placing Codex credentials in browser storage. A Tauri wrapper remains a later distribution option if a native keychain and local runtime become necessary.

## Next Steps

1. Define the Luna provider contract and confirm how Codex usage can be called from this app.
2. Design the event and artifact schemas for courses, assignments, agent runs, handoffs, learner signals, and profile updates.
3. Choose the first supported input set: assignment prompt, rubric, course notes, and draft.
4. Sketch the workspace states for intake, active run, automatic handoff, review, failure, and resume.
5. Define a small evaluation set of real course examples to test rubric grounding, Tutor adaptation, handoff quality, and learner-model updates.
6. Implement the Assignment-to-Tutor loop before adding research search, a third agent, or broad calendar automation.

## What I noticed about how you think

- You drew a hard boundary between “the chatbar” for organizing yourself and the agent workspace for “learning and tryna get a good grade.” That boundary is the product's central design decision.
- You did not settle for a single generic assistant. You asked for “seperate agents” and kept the Tutor and Assignment roles distinct.
- When the four assignment capabilities felt useful, you chose to combine them into one lifecycle instead of forcing an artificial single-purpose choice.
- You selected automatic orchestration and a durable runtime because you want the workspace to be useful now and also serve as a place to research agent behavior.
