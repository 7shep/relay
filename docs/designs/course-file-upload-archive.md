## Problem Statement

Relay currently reads syllabus uploads in the browser, sends extracted text to
local Qwen, and keeps only normalized assignments in browser storage. A PDF
uploaded to ChatGPT through the Assignment skill is only available to that
conversation. The same course file therefore has no durable, source-linked
home for later assignment guidance or study-memory context.

The requested behavior is one canonical local archive for both upload paths:

```text
study-context/
  courses/
    <COURSE>/
      materials/
        file-uploaded/
          <safe-original-filename>
```

`<COURSE>` is the existing uppercase display folder derived from a lowercase
course ID such as `cs-441`. The shorthand `study-context/class/file-uploaded`
means this course-scoped path; the approved bridge layout remains canonical.

## User Outcome

- Adding a syllabus still extracts dashboard assignments through local Qwen,
  even when the bridge is offline.
- The original syllabus bytes are proposed for immutable storage in the selected
  course's `materials/file-uploaded/` folder.
- Qwen returns class-routing evidence. When it cannot identify a class with
  enough confidence, Relay asks for the class name in the existing assistant
  sidebar and resumes the same upload instead of guessing.
- Uploading an assignment PDF in ChatGPT through the Assignment skill requests
  an explicit course code when needed, then hands the original PDF to Relay's
  assignment-file popup for local import into that course folder.
- No client or skill claims that a file was saved until the authenticated bridge
  reports a committed operation.

## Constraints

- The local bridge owns the durable `study-context` archive. Browser storage is
  only a compatibility cache.
- Original file bytes are immutable. Derived extracted text, assignment records,
  and manifest entries link back to the original artifact by ID and content hash.
- Writes remain proposal-based: visible proposal, explicit approval, short-lived
  exact approval token, then commit. Duplicate, cancelled, failed, and offline
  states remain visible.
- Course IDs are lowercase slugs for APIs; course display folders use the
  existing uppercase course code. User-provided class names must be normalized
  and validated before they become a path.
- The current bridge body limit is 2 MB. PDF uploads need a documented,
  configurable limit above the expected assignment/syllabus size, with a clear
  failure when the limit is exceeded. The implementation should not silently
  truncate or convert an original PDF to extracted text only.
- Assignment guidance must expose missing prompt, rubric, draft, material, or
  learner context. File ingestion must not create a dashboard task, submit work,
  overwrite a draft, or invent assignment metadata.

## Premises

1. Qwen is a classifier and extractor, not a file writer. It may return a
   course ID, display label, confidence, evidence, and unresolved status; Relay
   or the authenticated bridge performs storage.
2. Dashboard syllabus imports and ChatGPT Assignment uploads use the same
   material-artifact contract and destination path, even though their clients
   have different transports.
3. Class uncertainty is a blocking routing state. Relay asks the user in the
   side chat before creating a material proposal; it never silently files a
   document under a guessed course.
4. A source hash is the duplicate key within a course. A duplicate proposal is
   retained as a failed/no-overwrite operation and points to the existing
   artifact.
5. The Assignment skill must not assume it can write directly to Windows. It
   requests a user-confirmed course code, then uses an authenticated bridge
   handoff when available or a Relay manual-import popup that accepts the
   original PDF. It cannot claim a commit without a committed bridge response.

## Approaches Considered

### Approach A: Compatibility adapter

Extend the current syllabus importer and material-ingest runtime. Qwen's
syllabus response gains per-file class-routing metadata while retaining the
existing assignment array. The dashboard creates a visible material proposal,
and a new chat-resolution state collects a class name when routing is unclear.
The Assignment skill requests the course code, then reports a Relay approval
handoff. Relay's assignment-file popup accepts the original PDF when ChatGPT
cannot forward its bytes directly.

Effort: S, human ~2 days / CC ~30 minutes. Risk: Medium.

Pros:

- Smallest change that covers both requested upload sources and keeps current
  offline assignment extraction useful.
- Reuses the existing `proposeMaterialIngest`, approval token, artifact hash,
  and local-course boundary instead of creating a second archive.

Con:

- The dashboard and ChatGPT skill retain separate transport adapters until a
  later unified material protocol is warranted.

### Approach B: Unified material-ingest protocol

Define a single bridge endpoint and schema for all syllabus, assignment, rubric,
lecture, and past-test uploads, then migrate both clients to it.

Effort: M, human ~4 days / CC ~60 minutes. Risk: Medium.

Pros:

- Class resolution, hashing, manifest entries, duplicate behavior, and failure
  reporting have one long-term owner.
- Future material types can use the same contract without adding another client
  adapter.

Con:

- It expands the bridge contract before the requested syllabus and assignment
  flow has been proven end to end.

### Approach C: Local intake queue

Both clients submit approved upload packages to a local queue. The bridge later
classifies, deduplicates, and moves each package into its course folder.

Effort: L, human ~1 week / CC ~90 minutes. Risk: High.

Pros:

- Offline clients can retry a preserved upload package without losing the
  original file.
- Batch imports and additional file types get a reusable asynchronous intake
  foundation.

Con:

- Pending classification adds user-visible state and makes it harder to tell
  whether a file is already available to Assignment guidance.

## Recommended Approach

Choose Approach A. It is the narrowest complete change: both paths gain durable
file storage, the existing dashboard behavior remains compatible, and the
bridge's safety rules stay intact.

### Qwen syllabus contract

For each supplied file, Qwen should return a routing record containing:

- source filename;
- normalized lowercase `courseId` when the source states a clear class code;
- display `courseLabel` when available;
- a confidence value and short evidence such as a syllabus header or course
  number;
- `needsClassName: true` when no class is explicit or the evidence is too weak;
- the existing normalized assignment list for that source.

Qwen must not infer a class from an unrelated assignment title, filename alone,
or a weak similarity to an existing course. The existing assignment fields stay
compatible: `title`, `course`, `kind`, `dueAt`, and `weight`.

### Dashboard flow

1. Read each selected file and retain its original bytes plus extracted text and
   source hash before calling Qwen.
2. Run the updated syllabus prompt and validate one routing result per source.
3. If every source has a valid course route, show the extracted assignments and
   create a material-ingest proposal for each original file.
4. If a source has `needsClassName`, add a visible assistant message saying that
   Qwen could not identify the class and naming the file. The next assistant
   input is treated as the class answer, validated as a course ID/display name,
   and applied only to that pending upload. Process multiple unresolved files
   one at a time.
5. Keep parsing status and storage status separate. A bridge outage must not
   remove successfully extracted assignments; the UI must show that the file
   still needs archive sync or manual import.
6. Present the exact destination, filename, source hash, and derived assignment
   records in the existing proposal review surface. Only an approved commit
   writes the file and manifest entry.

### Assignment skill and manual PDF handoff

1. Resolve the named assignment and its course using the local manifest/course
   context. If multiple courses or assignments match, ask the learner to choose.
2. When the learner uploads a PDF, preserve the original PDF payload and its
   original filename. Extract text only as a derived field for guidance.
3. If the course code is not already explicit and unambiguous, ask for it in a
   blocking course-code popup before starting file storage. The popup must show
   the filename, explain the destination, validate a code such as `CISC301`,
   and require confirmation. It must not accept a guessed course from a title.
4. Once the learner confirms the code, Relay creates the course-scoped import
   destination as part of the normal material proposal/commit flow. The manual
   handoff supplies `sourceType: assignment`, course ID, filename, original PDF
   bytes, extracted text, assignment ID when known, and an idempotency key based
   on course plus hash.
5. If the ChatGPT transport can forward original bytes, the Assignment skill
   may send the proposal to the authenticated bridge. If it cannot, the skill
   must direct the learner to Relay's manual assignment-file popup, where the
   learner selects or attaches the same PDF and confirms the already supplied
   course code. Relay, not ChatGPT, creates the directory and sends the bytes to
   the bridge or local import path.
6. Show the proposed `materials/file-uploaded/` destination and tell the learner
   that Relay approval is still required. Do not say “saved” until a committed
   bridge response exists. If the bridge is unavailable, retain the pending
   status and offer the manual import route without claiming a write.

### Bridge and manifest contract

The existing material proposal/commit path should support the new destination
and both clients. The committed artifact manifest should include artifact ID,
course ID, source type, original filename, relative path, byte hash, import time,
parse status, and links to derived extracted text and assignment metadata.

The bridge must validate the course path, reject traversal and symlink/reparse
point escapes, sanitize the filename without changing the stored original-name
metadata, and refuse to overwrite an existing path. A same-content duplicate
should be reported as retained/no overwrite. Partial writes must become a
visible failed operation and must not be described as successful.

## Open Questions

- What upload size is appropriate for local syllabus and assignment PDFs, and
  should the bridge use a configurable 25 MB limit or a streaming/chunked path?
- Can the target ChatGPT skill transport forward original PDF bytes to the
  authenticated bridge as an optimization, or should every upload use the
  manual Relay popup?
- Should the dashboard show one combined multi-file proposal or one proposal
  per source file when multiple syllabi are selected?
- How should a user-created class name map to a stable course record when the
  class does not yet exist in the local course manifest?
- Should existing artifacts under `materials/originals/` be migrated, mirrored,
  or remain readable while new uploads use `materials/file-uploaded/`?

## Success Criteria

- A text syllabus and a selectable-text PDF still produce the same dashboard
  assignment results when the bridge is offline.
- A clearly identified syllabus produces a visible, approval-gated proposal and
  commits its original bytes to
  `study-context/courses/<COURSE>/materials/file-uploaded/`.
- An unclear syllabus causes a side-chat class prompt and cannot be committed
  until the user supplies a valid class.
- Multiple syllabus files route independently, so one uncertain file does not
  misfile the others.
- An Assignment skill PDF requests a course code when needed, and the Relay
  handoff popup creates/proposes the correct course path without title-only
  matching while preserving the original PDF.
- Duplicate, oversized, malformed, cancelled, offline, failed, and successful
  states remain distinguishable and never claim a write that did not happen.
- Manifest and derived assignment records link to the immutable source artifact.
- Tests cover Qwen response normalization, class uncertainty, class-answer
  validation, source hashing, destination safety, duplicate imports, approval
  and commit behavior, and Assignment skill contract wording.

## Distribution Plan

This remains part of the existing local Relay app and optional localhost bridge.
No hosted upload service is introduced. The repository's existing npm build and
bridge launch flow remain the distribution path; documentation must explain the
course-root configuration, authenticated write requirement, upload limit, and
manual fallback.

whose class is only known to you, and one assignment PDF uploaded through the
Assignment skill. Verify that each original file lands in the intended course
folder, that the uncertain case asks in the side chat, and that turning off the
bridge leaves assignment extraction usable without claiming the file was saved.

## What I noticed about how you think

- You stated the desired archive shape directly: “study-context/class/file-uploaded,”
  which makes the durable file location part of the product outcome, not an
  implementation detail.
- You connected two workflows, the dashboard's “add syllabus” path and the
  ChatGPT Assignment skill, instead of accepting two separate copies of course
  context.
- You specified the recovery behavior yourself: if Qwen cannot identify the
  class, it should ask in the side chat rather than silently guessing.
- You chose to build on the existing bridge design, preserving the project's
  local-first and approval-gated direction while adding the missing upload path.

## Reviewer Concerns

The required adversarial subagent review was unavailable in this environment.
The manual Relay popup is now the required fallback when ChatGPT cannot forward
original PDF bytes; direct byte transport remains an optional optimization. The
other main unresolved implementation risk is the current bridge's 2 MB request
limit.
